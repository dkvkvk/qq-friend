# SnowLuma

NTQQ 的「远程协议框架」：往真实 QQ 进程注入 hook，把原生会话通过 **OneBot v11** 暴露出来。

- 文档：<https://snowluma.github.io/>
- 仓库：<https://github.com/SnowLuma/SnowLuma>
- 定位：**只是协议端**，不含任何聊天逻辑

## 它是什么、不是什么

| 是 | 不是 |
|---|---|
| 登录 QQ、收发消息、暴露 OneBot 接口 | 聊天框架（那部分交给 AstrBot 等） |
| NapCat 的同类替代 | 大模型客户端 |

## 三种使用形态

1. **本地一体**：QA 机器上同时跑 QQ + 注入，登录扫码在同一个环境
2. **远程分离**：QQ 跑在能显示登录环境的机器，协议服务对外提供接口，框架在另一台机器上连
3. **Docker/VM 隔离**：把 QQ 关进容器或虚拟机，方便快照回滚

共同前提：**必须有一个能运行 QQ、能注入、能扫码登录的环境**——纯无头服务器做不到第一步。

## 接入步骤（通用）

1. 在目标环境装 QQ（NTQQ）并登录小号
2. 部署 SnowLuma，按文档完成注入 / 连接
3. 在 SnowLuma 里配 OneBot：
   - 正向 WebSocket（它开服务，框架来连）：记下端口和 token
   - 或反向 WebSocket（框架开服务，它去连）
4. 框架侧（AstrBot / NoneBot2 / 自写）填地址 + token
5. 自测：`/get_status` 或让框架发一条「在吗」

## 配置要点

- **token 用强随机**，别裸奔在公网；跨机走 SSH 隧道或内网
- 消息格式选 **Array**（数组消息段），字符串格式在新版里兼容性差
- 开 `reportSelfMessage`，否则「自己说的话」不会进上下文
- 群消息要额外开群事件上报

## 与 NapCat 怎么选

| | SnowLuma | NapCat |
|---|---|---|
| 生态与资料 | 新，文档少 | 老牌，遇到问题搜得到 |
| 配置 | 相对轻 | 选项多（WebUI） |
| 稳定性 | 取决于版本跟进 | 同样取决于版本跟进 |

**结论**：第一次搭，选 NapCat；已经跑起来了想换轻一点的，试 SnowLuma。

## 坑

- QQ 版本更新会打断注入，需要等协议端跟进
- 掉线不自愈：进程活着但会话已断，表现是「发出去没反应」
- 一个 QQ 号只能被一个协议端登录
- 容器里跑要注意扫码登录的显示环境
- 封号风险真实存在：用小号、控制频率、别做群发

## 合规提醒

注入式方案不属于官方接口，违反 QQ 用户协议，账号可能被限制或封禁。自用自己承担，别拿它做对外服务。
